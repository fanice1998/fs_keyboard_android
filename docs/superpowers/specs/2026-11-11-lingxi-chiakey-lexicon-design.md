# 千秋詞庫併入靈犀

日期：2026-11-11。個人研發，不散布、不分享。這份設計不處理授權。

## 目的

注音選字只留一份常駐詞庫。千秋 `unigrams` 裡、靈犀詞庫還沒有的詞，併進靈犀的詞庫，走同一條 `exact()`、Viterbi、候選列。千秋原生引擎和那份約 35 萬詞的 Java 部分詞庫不再為了選字留在行程裡。

這樣做是因為兩份詞庫同時常駐，整隻鍵盤行程約 387 MB。選字正確率仍優先於延遲，延遲仍優先於記憶體。併進去的詞不能把靈犀已有的常用詞擠出前八名。

## 目標

- 個人組出來的 APK，注音候選的詞來自動一份靈犀詞庫。這份詞庫含原本的靈犀列，加上千秋有、靈犀沒有的列。
- 同一個讀音若靈犀已有至少八個非罕見詞，前八名的統計排序與現在相同。補詞不進 Viterbi 的切詞。只有非罕見列少於八個時，才把完整讀音的補詞補進前八名的空位。
- 沒進前八名的千秋詞仍出現在組字區，點了可以上屏。上限 8 個，放在整句推薦之後、注音字片之前。
- 靈犀完全沒有該讀音時，千秋的詞可以成為前八名，Enter 會送出其中第一個蓋滿音節的詞。
- 鍵盤行程不再為選字開啟 `ChiaKeySession`，也不再建立 `PartialLexicon`。
- 自造詞、灰色預測、Enter、空白鍵、倒退鍵的現有規則不變。

## 不做

- 不改語言模型 `lm.bin`，不替千秋詞編造 bigram。
- 不改選字模型，不讓模型產生新詞。模型仍只重排統計前八名。
- 不把灰色預測接到語言模型裡沒有的詞。`bi() <= 0` 的詞仍然不會變成預測尾字。
- 不在每個按鍵查 SQLite。
- 不刪 `libfs_chiakey`、子模組、或手機上已有的 `files/chiakey/`。這一次只是選字不再打開它們。
- 不覆寫 `data/lingxi/data/lexicon.bin`。合併產物只進建置輸出。
- 不提交合併後的詞庫、千秋資料庫、或模型。
- 不把下一個詞用的 `assets/lexicon/lexicon.bin` 併進來。
- 英文與符號詞庫不動。

## 失敗條件

- 常見讀音的前八名被千秋詞蓋過，或因此整列跳過模型重排。
- 合併只做在記憶體的第二份表，千秋部分詞庫和原生引擎仍常駐。
- 字數和音節數不同的列進了 Viterbi。多音節時，前八名裡只要有一列的字數不等於音節數，模型會整列不做重排。

## 限制

- 靈犀 `exact()` 依音節 id 二分搜尋，列必須按讀音 id 排序。`byBody` 在建構時重排。`byText` 必須按表面字排序。
- Viterbi 丢掉 `prw <= 0` 的列。千秋的 `probability` 是對數（`你好` 為 `-0.927933`），必須先變成正的 prior。
- 音節數上限是 `MAX_WORD`（8）。`rdLen` 是一個 byte。
- 合併後的第一次 `byBody` 排序發生在靈犀載入執行緒，不在按鍵執行緒。
- CI 沒有這兩份資料。`-PbundleLingxi=false` 與 `-PbundleChiaKeyLexicon=false` 維持現狀。夾具測試在沒有全量詞庫時也要能過。
- `LingxiSelectTest` 仍直接讀 `data/lingxi` 的原始包，不讀合併產物。

## 做法

考慮過三條：

1. 開機另做一份補詞表，查詢時併進 `exact()`。詞進得了選字，但行程裡仍是兩套結構，和「併進靈犀這一份」不一樣。
2. 每個按鍵查千秋資料庫。記憶體最小。一句注音有多種切法，25ms 沒有把握。
3. 在個人組包時把千秋未重複的列寫進一份靈犀格式詞庫，手機只載這一份。選這條。原因是詞真的在靈犀詞庫裡，手機不再掃 35 萬列，原生引擎不必為選字打開。

## 合併規則

輸入是 `data/lingxi/data/lexicon.bin` 與 `data/chiakey/ChiaKeySource.db` 的 `unigrams`（`qstring`、`current`、`probability`）。`qstring` 用現有的 `BopomofoOrder.decode` 轉成注音音節。解不出來的列丟掉。

留下的列要同時滿足：

- 音節數在 1 到 8。
- 表面字的 Unicode 字數等於音節數。字數不同的列不進詞庫，避免模型整列跳過。
- 表面字不是空的。
- 同一表面字加同一串讀音，靈犀已經有：留靈犀那一列，不改它的 prior、罕見標記、旗標。

新列：

- prior = `exp(probability)`，再夾到 `[1e-6, 1]`。`probability` 一律當成自然對數。
- 罕見標記設為真。前八名仍先由非補詞決定；罕見只在非補詞少於八個、補詞被補進空位時參與排序。
- 補詞旗標設為真。靈犀原列的這個旗標維持假。Viterbi 與 `longer()` 看這個旗標跳過，不靠罕見標記代替。
- 讀音裡靈犀沒有的音節，加到音節表尾端，取得新的 id。接著整份詞庫按讀音 id 重排，重建 `byText` 與 `byBody`。

旗標放在現有的 `flags` byte。目前程式只讀 bit 1（值 2）當罕見。合併前先數原始詞庫的旗標值，選一個原始列都沒設的 bit 當補詞旗標。預設用 bit 2（值 4）。若該 bit 已被使用，改用下一個空的 bit。不因此改詞庫版本號。

產物寫到建置輸出的 `lingxi/lexicon.bin`，並寫一個標記檔 `lingxi/lexicon.merged`。不要改 `data/lingxi/` 裡的原始檔。個人組包不再把 `ChiaKeySource.db` 打進 APK。標記檔不在時，維持現在的載入：靈犀原始詞庫，千秋仍作退路。

手機上若已有 `files/chiakey/writable/SmartMandarinUserData.db` 的 `user_unigrams`，載入靈犀時用同一套規則併進記憶體裡的詞庫。這份檔只在手機上，組包時沒有。用唯讀 SQLite，不打開原生引擎。沒有這個檔就跳過。

## 候選列

`LexHit` 增加 `supplement`，預設假。查詢要能把它和原列分開。

Viterbi 的切詞不走補詞。常見音節在千秋有兩千到四千列；若每段都拿去算分數，按鍵會超過 25ms，模型重排也會整列跳過。波束只用 `supplement == false` 的列，這一段和現在的靈犀詞庫相同。

整句的統計列出來之後，若非罕見列少於八個，才把這個完整讀音的補詞依同樣的分數公式補進空位，補到八個或補詞用完為止。補的是整段讀音，不是每個子切分。字數已經規定等於音節數，所以模型重排的條件和現在一樣。

`longer()` 數那 32 個更長的詞時跳過補詞。補詞沒有 bigram，本來就不會變成灰色尾字；若留在前 32 名裡，現在看得到的預測詞會被擠掉。跳過它們，灰色預測維持原樣。

較短詞最多 8 個、第一音節單字最多 48 個，仍只取非補詞，避免千秋的 prior 把現在的單字擠掉。單一音節的千秋字由下面的完整讀音補詞負責。

`withChoices` 在整句列之後、注音字片之前，加入這個完整讀音的補詞：還沒出現在整句列裡的，按 prior 由高到低，最多 8 個。`span` 等於目前音節數。不是預測字片，不是注音字片。這一步只濾已排序好的同一讀音區間，不把補詞放進波束。

組字區順序成為：預測字片、自造詞、整句前八名、最多 8 個千秋補詞、剛打的注音、較短詞、第一音節單字。Enter 仍取第一個蓋滿開放音節、且不是預測、不是注音字片、不是剪貼簿的列。補詞排在整句之後，所以靈犀有蓋滿的詞時，Enter 不會改送補詞。

未完成的下一音節仍留上一列，規則不變。補詞不另跑模型。

## 啟動

個人包有 `lexicon.merged` 時，`FsKeyboardService` 不呼叫 `ChiaKeyRuntime.session`，不跑千秋開啟與部分詞庫掃描。靈犀載入執行緒 decode 合併後的詞庫，必要時再併 `user_unigrams`，然後才公布引擎。公布前的按鍵仍走現有的「引擎還沒好」路徑；這段時間沒有部分詞庫，候選只有注音字片，直到靈犀公布。

沒有標記檔時，啟動路徑與現在相同。

`onDestroy` 仍不關閉原生引擎。這次的個人包根本不開啟它。

## 測試

用小夾具，不依賴全量檔：

- 靈犀已有的表面字加讀音，合併後 prior 仍是靈犀的。
- 千秋對數機率變成 `(1e-6, 1]` 的 prior，Viterbi 不會因為 `prw <= 0` 丟掉它。
- 字數不等於音節數、音節數超過 8、解不出的 `qstring`，都不進詞庫。
- 新音節可以查到。
- 同一個讀音已有八個非罕見詞時，補詞不進統計前八名，也不進切詞波束。
- 這個讀音在靈犀沒有詞時，補詞可以成為第一列。
- 已有灰色預測的前綴，補進更長的千秋詞之後，預測尾字仍是原來那個。
- 組字區在整句之後、注音字片之前出現該補詞，且不重複前八名裡已有的表面字。較短詞與第一音節單字的成員不因補詞改變。
- Enter 在靈犀有蓋滿詞時仍送靈犀那列；靈犀沒有時送補詞。

全量檔的合併不進 CI 必跑斷言。原始 `LingxiSelectTest` 繼續讀未合併的 `data/lingxi`。

## 留給實作時決定

- 空旗標 bit 的最終選擇，以原始 `lexicon.bin` 的旗標統計為準。
- 合併工作放在 Gradle 工作還是被該工作呼叫的 Kotlin 程式。產物路徑與「不覆寫原始檔」不能改。
- `user_unigrams` 併入時的暫存物件怎麼在公布引擎前釋放。
